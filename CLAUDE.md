# CLAUDE.md (Warden)

Warden is one Python package (`warden/`) that runs on Windows and macOS, plus its tests,
config, templates and packaging. Windows is built on the user's PC; the Mac app is built
only by GitHub Actions and shipped as a DMG.

## Every prompt, before anything else
1. Read the **"Current status"** block at the top of `PROGRESS.md`. It names the next stage.
2. Read `PRINCIPLES.md` (how we work, hard limits, quality gates) and `HANDOFF.md` sections
   **0–3** (rules, clean-room rules, goal, stack). They're short.
3. Read the **next stage's entry** in `HANDOFF.md` §10 "Stages", plus every section it links to.
   Mac stages also need `warden-mac-handoff.md`. Stages tagged **[design]** need an `approved`
   note in `docs/design/` before any code.
4. Only read older parts of `PROGRESS.md` (stage log, decisions, history) if the stage needs them.
   Don't read either file in full "just in case". That wastes tokens on every prompt.

## One prompt = one stage (max ~30 minutes)
- Run `date` when you start and note the time. Run it again before each big step.
- Do **only** the next stage. Don't start the stage after it, even if there's time left.
- At ~25 minutes, if the stage isn't finished, stop at a safe point. Log it as **PARTIAL** with
  exactly what's left, and make the leftover the next stage.
- If a stage is clearly too big, split it in `HANDOFF.md` §10 (M5 → M5a, M5b), log the split as a
  decision, and do the first part.
- A stage tagged **(needs the user)** ends when the user's part is ready: hand back what they have to
  do (in plain steps, no Terminal on a Mac) and stop.

## Every stage ends with all of these, in order
1. **Add a permanent smoke check**: at least one script in `smoke_checks/`
   (e.g. `smoke_checks/m5_hotkeys.py`) that proves this stage's feature still works and exits
   non-zero if not. It stays forever, so every later stage re-checks it. No Roblox, no real
   window, no real input: fakes only.
2. **Smoke test.** Run `python scripts/smoke.py` (it re-runs itself with `.venv` if there is one).
   It must print `SMOKE: PASS`. It runs every smoke check, `warden --selftest` and the full pytest
   suite, writes `.smoke/last-run.json` and regenerates `STATUS.md`. If smoke fails and you can't fix
   it in time, log the stage as FAILED or PARTIAL. **Never mark a failing stage done.**
3. **Verifier.** Run the `verifier` subagent with the stage ID. It didn't write the code, so it checks
   the work with fresh eyes and runs smoke itself. If it says FAIL, fix what it lists and run it again
   (max 2 rounds, then log PARTIAL).
4. **Update `PROGRESS.md`:** the "Current status" block, a new stage-log entry (template in
   `PROGRESS.md`, with the `Smoke test:` and `Verifier:` lines), and tick the stage in `HANDOFF.md` §10
   and in `PROGRESS.md` "Stages". Keep the headings exactly as they are; `scripts/progress_view.py`
   reads them.
5. **Commit and push:** `git add -A`, `git commit -m "<id>: <what> (<HANDOFF ref>)"`, `git push`.
   If the stage changed anything the Mac build uses, the push is what tells you whether CI is green:
   check the "Mac release" run when a tag is involved.
6. **Hand back** in 8 lines or fewer: stage done/partial, smoke result, verifier verdict, next stage,
   and anything the user has to do. Then stop.

A Stop hook (`.claude/hooks/stage_gate.py`) checks steps 2, 4 and 5: committed, pushed, PROGRESS
updated with Smoke and Verifier lines, and a passing smoke run newer than the last code change. If it
sends you back, fix what it says. Don't argue with it, and don't weaken it or its tests.
A PreToolUse hook blocks edits to the harness itself (`.claude/`, `scripts/smoke.py`,
`scripts/progress_view.py`, `scripts/harness_common.py`, `scripts/known_env_failures.json`); if one
really needs changing, tell
the user what and why instead. A SessionStart hook prints the time and the next stage.
`STATUS.md` is generated by the smoke runner; never edit it by hand.

## Hard limits (PRINCIPLES.md §4)
- Never commit code with failing tests. (`scripts/known_env_failures.json` lists the only tests allowed
  to fail, and only on the OS named there. Never add to it to get a stage through.)
- **Never change how Windows behaves** in a Mac stage. Mac code goes behind the platform seams or
  `sys.platform == "darwin"`.
- Never mix feature changes and refactoring in one stage. Refactors are their own `R-n` stages.
- All code traces back to a HANDOFF section (or a design note). Commit messages carry it:
  `M5a: fix title-bar offset (warden-mac-handoff §7 step 4)`.
- Quality gates: new code is covered by tests; every new public function has at least one test.
- Clean-room rules (HANDOFF §1) still apply. Nothing that works around Roblox's anti-cheat, macOS
  privacy permissions, Gatekeeper, or device management.

## Commands
`/stage` (same as "continue") · `/design <feature>` · `/bugfix <id>` · `/refactor <what>` · `/retro`.
Subagents: `verifier` (critic) and `test-writer` (red tests first).

## Don't stop to ask questions
Pick a sensible default, record it under **Decisions** in `PROGRESS.md`, and keep going.
`HANDOFF.md` §12 lists things the user will confirm later. Only stop for things marked
**(needs the user)**: live Roblox tests, the real-Mac checklist, pushing tags, GitHub settings,
Gumroad or Discord accounts.

## Safety rule for testing (learned the hard way: PROGRESS.md History → Decisions #29)
Anything that sends clicks or keys runs **observe-only** in every test and smoke run: it logs what it
*would* press. Smoke sets `WARDEN_FORCE_OBSERVE_ONLY=1` and a temp `WARDEN_HOME`, so nothing touches
the user's real config or their Roblox window. Never call `TickLoop.start()` or `MainWindow._start()`
outside a test, and never write to the repo's `config/` or `templates/` from a test (History → Decisions #30, #45).
Live runs happen only when the user starts one, on an **alt account**.

## Fixing bugs the user reports
0. Create `docs/bugs/BUG-NNN-<name>.md` from `docs/bugs/TEMPLATE.md` with the user's words.
1. Find evidence first: the session log (`%LOCALAPPDATA%\Warden\logs`, or
   `~/Library/Application Support/Warden/logs` on a Mac), saved unknown frames, a failing test.
   Don't fix a guess.
2. Write a regression test that fails (red). Recorded frames go in `fixtures/frames/`.
3. Fix it until the test passes (green).
4. Run the whole smoke suite so nothing else broke.
5. Record the root cause in `PROGRESS.md`.

If the bug can only be seen live ("the click didn't register", "it rejoined forever"), say so. Don't
claim it's fixed because the offline tests pass; add it to "Live tests needed" in `PROGRESS.md`.
